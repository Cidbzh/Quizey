# Quizey — vérification détaillée (`_qz_verify.js`)

Fiche de référence de la section « Tests » du `CLAUDE.md` projet. À lire avant de toucher au moteur (bascule matière, boot cascade, stats) ou d'ajouter un générateur.

## Vérification complète

```bash
node _qz_verify.js
```

Le script compile les **deux** blocs `<script>` (anti-flash + principal) via `vm`, puis teste fonctionnellement sur un DOM factice :

- **Thème** : défaut `auto`, clics Auto/Clair/Sombre, persistance `qz_theme`, rechargement (+ le fallback du script anti-flash sur l'ancienne clé `cz_theme` — section [2]).
- **Fumigène** `confetti()`.
- **Section [7] — générateurs** : chaque générateur des **quatre matières** — maths/PC **par année** (Seconde, Première, Terminale) + le **pool « Maths expertes »** (case à cocher sur Terminale, 3 thèmes) + DE + EN — est lancé **25×** :
  - forme de la question ;
  - auto-cohérence `checkAnswer()` avec sa propre réponse (réponses saisies) ;
  - **contrat QCM** (tous les générateurs choice, maths + PC + DE + EN) : options non vides et deux à deux distinctes, et l'index de la bonne réponse **non constant** sur les 25 tirages — la preuve des options mélangées via `shuf()` : avec ≥2 options, un index constant sur 25 tirages a une probabilité ~(1/n)²⁴, c'est la signature d'un générateur non converti au helper `qcm()`, pas de la chance ;
  - rendu des visuels SVG en phases `"q"` et `"c"` ;
  - round-trip `JSON.parse(JSON.stringify(q))` qui simule le mode révision après un rechargement — c'est ce qui détecte les fonctions ou `undefined` glissés dans les specs `viz`.
- **Section [8] — régression de bascule** : après `setMatiere("pc")` + une bonne réponse PC :
  - `qz_stats` (maths) reste **bit-à-bit inchangé** ;
  - `qz_stats_pc` est incrémenté (1 réponse / 1 bonne) ;
  - le retour maths restaure les stats à l'identique.
- **Section [9] — câblage du basculeur** : page ouverte en PC (`data-mat="pc"` sur `<html>`), les listeners `click` doivent porter **uniquement** sur les deux boutons `.seg-btn` : le test asserte que `<html>` n'a **aucun** listener `click` (un sélecteur `[data-mat]` sans `.seg-btn` l'inclurait, et la bulle d'événement rebasculerait tout clic « Maths » sur PC — le DOM factice ne simule pas la bulle, d'où l'assertion sur le listener lui-même). Puis clic « Maths » → `state.matiere="maths"`, `data-mat` retiré, et `html.boot` **ré-armée** (la cascade d'arrivée rejoue à chaque bascule — la pré-condition « boot retiré » est simulée avant le clic, sinon l'assertion passerait même si `swap()` ne ré-armed rien).
- **Section [10] — bascule EN PLEINE cascade** : bascule alors que `boot` est encore active (état réel, **sans** la simulation de [9]), avec des timers suivis/annulables et un journal des opérations `classList` sur `<html>` : asserte que `boot` est retirée **puis** réajoutée (la seule façon de redémarrer l'animation CSS — un simple `add()` est un no-op si la classe est déjà là), qu'**un seul** timer de retrait (2800 ms) reste vivant, et que l'ancien timer du premier chargement (annulé) ne coupe pas la nouvelle cascade à T+2800 ms — le garde-fou de l'animation « unique » : seule la dernière cascade et son timer survivent, quelle que soit la cadence des bascules. Le cycle de vie classe+timer est centralisé dans `rearmBoot()` (Quizey.html), appelé à la première visite **ET** depuis `setMatiere()` — ne pas ré-introduire de `setTimeout` de retrait de `boot` ailleurs.
- **Section [11] — pas de temps mort** : sans reduced-motion (`matchMedia` par défaut `matches:false`), le clic sur « Maths » doit swaper de façon **synchrone** (`data-mat` retiré, `boot` active, aucune classe `home-out`/`home-in` sur `#home`) : l'ancienne chorégraphie de sortie 230 ms (homeOut/homeIn) est supprimée, ne pas la ré-introduire. Les délais de la cascade doivent aussi être **compressés au clic** (`--boot-k=.45` posé sur `<html>`, absent à la première visite) : le premier mouvement part quasi immédiatement après le clic, la chorégraphie complète (×1) reste réservée au premier chargement.

- **Section [12] — bascule DE** : miroir de [8] pour la 3e matière, avec deux renforcements : `qz_stats_pc` **aussi** doit rester bit-à-bit inchangé après une réponse allemande, et — l'allemand étant 100 % QCM — la bonne réponse passe par le **vrai chemin moteur** `answerChoice(state.q.correct, …)` (et non `afterAnswer()` direct) : l'option `q.correct` doit être acceptée, `qz_stats_de` incrémentée (1 réponse / 1 bonne), `qz_stats` et `qz_stats_pc` intacts, et le retour maths restaure les stats au bit près. Le mode « Sprint » n'existe plus : `#secSprint` doit être **absent** du DOM (le DOM factice auto-crée tout `#id` touché, l'assertion porte donc sur `env.byId.secSprint === undefined`).
- **Section [13] — basculeur 4 matières** : page ouverte en allemand (`data-mat="de"` sur `<html>`), les listeners `click` doivent porter sur les **quatre** boutons `.seg-btn` (Maths / Physique-Chimie / Allemand / Anglais) et `<html>` doit en avoir **aucun** (même garde-fou que [9] : le sélecteur câblé doit être `.seg-btn[data-mat]`, jamais `[data-mat]` seul — le DOM factice ne simule pas la bulle, l'assertion porte donc sur le listener lui-même). Clic « Maths » → `state.matiere="maths"`, `data-mat` retiré, cascade réarmée ; clic « Allemand » → `data-mat="de"` reposé (accent vert), bouton « Allemand » seul marqué `.on` ; clic « Anglais » → `data-mat="en"` (accent rouge), bouton « Anglais » seul marqué `.on`.

Cette section a aussi fait remonter un bug réel (corrigé) : `bySub` n'était pas normalisé dans `loadStats`, un objet sauvegardé sans ce champ faisait planter `renderHome`.
- **Section [16] — suppression « Grandeurs cosmiques », orphelines purgées** : un utilisateur PC ayant une question à réviser ET des entrées d'historique rattachées au thème `cosmo` (retiré du registre le 2026-08-20) ouvre l'app : `loadStats()` purge ces orphelines (la question « vivante » d'un autre thème reste, l'historique `newton` est intact) — sans ce filtre `renderQ()` planterait sur `r.sub.name` (`sub` undefined) et un point faible `cosmo` lancerait un thème aléatoire. `vzRatio`/`"scale"` restent dans `VIZdraw` (inoffensif ; specs déjà persistées chez les anciens utilisateurs).
- **Section [17] — version d'interface (détection, bascule, persistance `data-ui`)** : la détection « téléphone/ordinateur » repose sur trois valeurs du sandbox (`innerWidth`, `matchMedia("(pointer:coarse)")`, `navigator.userAgent`) que le test pilote par appareil factice :
  - **ordinateur** (1440 px, souris fine, UA desktop) → `detectUI()==="d"`, `data-ui` ABSENT de `<html>`, `qz_ui="d"` persisté, bannière restée cachée ;
  - **téléphone** (390 px, tactile, UA iPhone) → `detectUI()==="m"`, `data-ui="m"` posé, bannière « Version téléphone activée » **affichée au 1er passage auto** ; clic sur son bouton « Version ordinateur » → `data-ui` retiré, `qz_ui="d"` persisté, bannière fermée ;
  - **tablette large** (1024 px, tactile, UA Mac sans « Mobile ») → reste `« d »` : le tactile seul ne suffit pas, il faut tactile **ET** <900 px, ou un UA mobile (couvre l'iPhone en paysage) ;
  - **choix explicite** : `qz_ui="m"` déjà sauvegardé sur un grand écran → la version téléphone **reste** (le choix gagne toujours sur la détection) et la bannière ne se réaffiche **pas** ;
  - **stabilité des stats** : avec les quatre clés `qz_stats`/`qz_stats_pc`/`qz_stats_de`/`qz_stats_en` pré-remplies, `setUI('m');setUI('d');setUI('m')` laisse les quatre **bit-à-bit identiques** — seule la clé `qz_ui` bouge (l'UI ne doit JAMAIS écrire dans les stats) ;
  - **anti-flash** : le script de tête (exécuté seul, avant le rendu) pose `data-ui="m"` sur `<html>` dès que `qz_ui="m"` est lue — pas de flash de « version ordinateur » au chargement sur téléphone.

- **Section [18] — niveau « Auto »** : `autoLevel(id)` évalue les **8 dernières réponses de ce thème uniquement** dans `stats.history` : moins de 3 réponses → « moyen » (on ne devine pas une performance qu'on n'a pas) ; < 50 % → « facile » ; 50–80 % → « moyen » ; ≥ 80 % → « difficile ». L'évaluation est par thème (un thème performant n'aide pas l'autre) et à fenêtre glissante (les fautes anciennes sortent du calcul).
- **Section [19] — répétition espacée (échéance, graduation, migration)** :
  - **migration** : un item ancien sans `due`/`reps` (utilisable avant l'espacement) est normalisé au 1er chargement → `due=0` (dû immédiatement), `reps=0` ;
  - `reviewAdd` → l'item entre avec `due=0`, `reps=0` ; `reviewAdvance` → `reps` s'élève, `due` repoussé selon la rampe `REVIEW_LADDER` (1ᵉʳ avancée ≈ +1 j), et l'item n'est plus « dû » (`reviewDueCount()`=0) ; `reviewReset` → `reps=0`, `due` ≈ +1 j ;
  - **graduation** : 4 réussites d'affilée → encore présent ; 5ᵉ → l'item est **acquis** et quitte la liste.
- **Section [20] — câblage afterAnswer → répétition espacée (mode libre + révision)** : en **libre**, mauvaise réponse → `reviewAdd` (l'item entre, `due=0`), bonne réponse → `reviewRemove` (la liste redevient vide). En **révision**, la question rendue est l'item **échue** (`reviewDue()[0]`) et **le compteur affiche le nombre d'échues**, pas la liste totale : avec 1 échue + 1 replanifiée demain → « 1 restant(s) » (l'ancien code affichait `stats.review.length` = 2 — régression corrigée 2026-08-22). Mauvaise réponse → `reviewReset` (conservé, `reps=0`, `due`≈+1 j) ; bonne réponse → `reviewAdvance` (`reps` s'élève, `due` s'éloigne).
- **Section [21] — dédup QCM (régression 2026-08-22)** : la clé de dédup `qKey` doit identifier la question **pédagogique**, pas le tirage. Trois questions `choice` : A et B ont même prompt, mêmes 4 options et même bonne réponse, **mais un ordre d'options différent** (les QCM sont mélangés à chaque tirage) ; C a un prompt différent. On attend **2 entrées** dans `stats.review` (A+B fusionnées), et qu'une bonne réponse sur B **retire** l'entrée ajoutée via A (l'ordre a changé entre-temps — l'ancien `JSON.stringify(q)` ne la trouvait pas et la conservait). `reviewAdvance` sur B doit aussi retrouver l'entrée ajoutée via A (`reps=1`).
- **Section [22] — points faibles, ex æquo (régression 2026-08-22)** : `weakPoints()` trie les cellules thème×niveau (≥ 5 réponses) par précision. En cas d'**ex æquo** (même % de réussite), le tiebreaker doit être le **nombre de réponses** (la cellule la plus répondue est la plus significative) — pas un comparateur sur un champ absent (NaN, tri inert). Deux cellules à 40 % : « bb » (10 réponses) doit sortir **devant** « aa » (5 réponses).
- **Section [23] — bascule EN (4e matière) + libellés de niveau langues (2026-08-22)** : miroir exact de [12] pour l'anglais — stats maths **et** allemandes bit-à-bit intactes après une réponse EN via le vrai chemin moteur `answerChoice()`, `qz_stats_en` incrémentée (1 réponse / 1 bonne), `data-mat="en"` posé sur `<html>` (accent rouge), le mode « Sprint » absent du DOM, question EN bien de type `choice`, et retour maths stats restaurées au bit près. Plus les **libellés CECRL** : `lvlLabel()` mappe les clés internes `facile`/`moyen`/`difficile` sur **A2 / A2+ / B1** en allemand et en anglais, et sur **Facile / Moyen / Difficile** en maths/PC — les clés internes ne changent pas (c'est ce qui garde les stats persistées valides), seul le libellé affiché change. `paintLvlButtons()` (relibellage des tuiles au rendu) doit être définie.
- **Section [24] — registres par année (refontes maths **et** PC 2026-08-23 sur les programmes officiels BO)** : `SUBJECTS_MATH`/`SUBJECTS_PC` sont des objets `{seconde,premiere,terminale}` (maths porte en plus `experte`, le pool de la case à cocher — [31]). La section vérifie : les **ids** (Première maths = 9 ids `p1_log`/`var`/`suites`/`equa2`/`deriv`/`logexp`/`trig`/`vect`/`proba`, Première PC = 13 ids dont 6 historiques + 7 nouveaux `p1_*` — dont `p1_stoich` : la stœchiométrie est en **PREMIÈRE**, pas en Seconde (Cid, 2026-08-23, ex-`s2_react`), préfixes `s2_`/`t_` sur Seconde/Terminale) ; que **chaque thème maths/PC porte facile+moyen+difficile** (aucun niveau « experte » restant) ; que `THEME_BY_ID` couvre tous les thèmes de tous les registres (maths/PC × année + DE + EN) ; les **volumes livrés 6/9/8 en maths, 9/13/13 en PC** (Seconde/Première/Terminale) ; que le pool maths « expertes » compte **3 thèmes** (complexes, arithmétique, graphes) et que PC n'en a **pas** ; que l'ancien thème « Limites » (`lim`) est **purgé** de `THEME_BY_ID` ; et que `loadStats` **purge les orphelines** (une entrée `review`/`history`/`bySub` rattachée à un id supprimé — y compris `s2_react` — est retirée au chargement, les ids vivants restent). Le contrat des générateurs (forme, `checkAnswer()`, QCM, SVG, round-trip) est couvert par [7] — qui y inclut le pool « Maths expertes ».
- **Section [25] — courbe de niveau (leveling)** : `xpCum(n)` (coût pour ATTEINDRE le niveau n : `25·n·(n+1) − 50` pour n ≥ 2, `xpCum(1)=0`) et `levelOf(xp)` forment une paire d'allers-retours : `levelOf(xpCum(n)) = n` pour n = 1…50, valeurs bornes vérifiées (0→1, 99→1, 100→2, … 1750→8), **monotonie** sur 0…2000, et `lvlInfo` renvoie toujours `n ≥ 1` avec `pct ∈ [0,1[` (1000 valeurs d'essai).
- **Section [26] — raccordement XP (UNE XP PAR MATIÈRE) + montée de niveau** : les clés sont `qz_xp` / `qz_xp_pc` / `qz_xp_de` / `qz_xp_en` — en **libre ET révision**, une bonne réponse n'écrit que la clé de la matière active et l'augmente de **exactement** les points de la correction (5/10/15 selon le niveau de la question + 5 si série ≥ 3) ; mauvaise réponse et « Passer » la laissent **inchangée**. **Montée de niveau (2026-08-23)** : un franchissement de palier appelle `levelUp()` **une fois** — l'animation de montée de niveau **remplace les confettis au palier** (les confettis restent à la fin de la révision, `endReview`) ; sans palier, `levelUp` n'est pas rappelé. La **carte hero** (`#lvlSlot`) affiche « Niveau N » + barre `aria-hidden` + « x / y XP », passe de N à N+1 au palier sans jamais fuiter de maths vers DE. Le panneau **« Par thème »** (`#bySubSlot`) est **toujours affiché**, même à zéro réponse (régression « le bloc disparaît » corrigée — les ids changent avec l'année, il ne doit donc pas disparaître dès qu'une année n'a pas encore de stats). Indépendance : une réponse DE/PC n'écrit JAMAIS `qz_xp` (maths), et inversement.
- **Section [27] — année (état, clés, indépendance maths/PC, sélecteur)** : clé absente **ou corrompue** (`"bac-pro"`, `"SECONDE"`) → `"premiere"` (le contenu historique reste la valeur par défaut — zéro migration) ; `setAnnee('invalide')` est ignoré ; `setAnnee` persiste **par matière** (`qz_year_math`/`qz_year_pc`) et les deux valeurs **coexistent** (maths « seconde » + PC « terminale » — indépendance) ; DE/EN → `state.annee === null`. Et maintenant que les quatre registres sont livrés (`yearReady()` = les 3 années non vides) : `#yearRow` est **visible** en maths et PC, **masqué** en DE/EN ; la ligne d'indication classe/matière ayant été retirée (2026-08-22), l'assertion porte sur l'**absence** de `#heroEyebrow` et sur la phrase de base identique quelle que soit l'année (`#heroLede`).
- **Section [28] — hero : pas de ligne classe/matière, phrase de base unique par matière (2026-08-22, sur demande)** : la ligne d'indication (eyebrow) est retirée de **toutes** les matières — `#heroEyebrow` absent du DOM, le code ne le référence plus — et `#heroLede` porte la phrase de base de la matière, **identique quelle que soit l'année** : vérifiée pour les 4 matières (maths « Pour réussir en maths, il faut pratiquer… », PC « …relier les formules aux situations… », DE « …se familiariser avec la langue… », EN « …entendre la langue, la lire et la réutiliser… »), au boot **et** après `setMatiere`/`setAnnee` (maths/PC × année).
- **Section [29] — doublons hérités de la liste à réviser (2026-08-22, bug signalé par Cid)** : un localStorage hérite de **2 entrées identiques** de la même question (ajoutées par l'ancien `qKey` avant la dédup [21]) → au chargement il n'en reste **une seule**, la **plus avancée** (`reps` max — la progression espacée est intacte), au contenu pédagogique retrouvé via le `qKey` actuel ; une bonne réponse sur cette question élimine alors **toutes** les échéances (avant la correction, la double écriture la faisait revenir en boucle).
- **Section [30] — puce de niveau dans la barre (2 modes)** : l'écran de question affiche « Niv. N » en **libre et révision**, avant et après la réponse ; une bonne réponse qui franchit un palier passe la puce de N à N+1 **immédiatement** (re-rendue par `gainXp`) ; la bascule de matière (maths → DE) affiche le niveau **DE** — l'XP est par matière, jamais partagée.
- **Section [31] — case « Maths expertes » (2026-08-23, sur demande de Cid — ex-4ᵉ année maths)** : « Expertes » n'est **plus une année** — c'est une **case à cocher** dans le bloc « Entraînement libre », visible **uniquement en maths × Terminale** : cochée, elle ajoute les **3 thèmes** du programme officiel des maths expertes (complexes, arithmétique, graphes & chaînes de Markov) au pool de Terminale (8 → 11 thèmes). Règles vérifiées — **structure** : `SUBJECTS_MATH.experte` = exactement 3 thèmes (`t_arith`/`t_complexes`/`t_graphes`), `SUBJECTS_PC.experte` **absent**, et les 12 questions expertes sont renivelées **facile/moyen/difficile** (aucun niveau « experte ») ; **années** : `yearsFor()` renvoie **3 années partout** (maths/PC/DE/EN — plus de 4ᵉ année) ; **migration** : `qz_year_math=« experte »` (valeur héritée) → `readYear('maths')=« terminale »` **et la case est cochée** (`qz_experte_math=true`) ; `qz_year_pc=« experte »` → `« premiere »` (PC ne la porte jamais) ; DE/EN → `null` ; valeur corrompue → `« premiere »` ; `yearReady('maths')`/`('pc')` = `true`, `('de')`/`('en')` = `false` ; **`setAnnee('experte')` est refusée partout** (maths et PC — « experte » n'est plus une année) ; **effet** : `activeSubjects()` maths/Terminale = 8 thèmes sans case, **11** cochée (les 3 expertes inclus) — sans effet en PC/Terminale (13) ni en maths/Seconde (6) ; **tirage** : 99 tirages avec case cochée → **tous** dans les 11 thèmes, niveaux **réels** (jamais « experte »), les 3 thèmes expertes servis par le mélange ; **UI** : la ligne « Maths expertes » occupe **un espace réservé en maths à toutes les années** (classe `.off` = `visibility:hidden` — pas de saut de mise en page au choix de Terminale), **visible uniquement en Terminale**, et **absente** (`hidden`) en PC/DE/EN ; cochage/décochage → `state.experte` + persistance `qz_experte_math` + **poche ré-ouverte** (`bagKey()` change) ; valeur corrompue → `false` (jamais d'erreur) ; **Auto** plafonne à « difficile » (100 % de réussite) — il ne propose **jamais** « experte » ; **scoring** : une bonne réponse « facile » rapporte **+5 XP** (pas 20). `PTS_LVL.experte=20` et `LVL_NAMES.experte=« Experte »` restent **en lecture** (légacy, pour les lignes `history` héritées) mais ne servent plus à aucun contenu neuf.
- **Section [32] — anti-répétition (shuffle-bag, 2026-08-23)** : en mode libre, le tirage ne pioche plus un thème « avec remise ». Une **poche** (`genBag`, en mémoire, jamais persistée) regroupe toutes les questions disponibles du tirage courant — chaque thème visible (ou verrouillé, ou multi-sélectionné) × niveau cible (Auto = niveau adapté au thème) — et chaque question est servie **une seule fois** avant remélange de la poche. Tests : **A** mix — N tirages (N = nombre de générateurs disponibles au niveau) → N générateurs **distincts**, puis la poche se remélange (le tirage suivant reste valide) ; **B** verrouillé sur un thème — 6 tirages → **tous** ce thème (pas de fuite) ; **C** « difficile » — tirage valide (sujet + prompt non vide + type), qui exerce le repli « aucun générateur au niveau → tous » ; **D** multi-sélection de 2 thèmes — 12 tirages → **uniquement** ces deux thèmes, et les deux sont servis. Le mode **review** est hors poche (il sert l'échue `reviewDue()[0]`). Note API : `state.sel` (tableau d'ids, vide = mix) remplace l'ancien `state.subject` (string) — session-only, **aucune migration**.

**CI GitHub Actions** : la suite tourne automatiquement sur `main` et les PR via `.github/workflows/verify.yml` (Node 22, `node _qz_verify.js`). Aucune dépendance à installer — le fichier de test n'utilise que `vm`, `fs` et un DOM factice.

**Historique** : ce script remplace l'ancienne vérification `awk`, qui n'extrayait qu'un seul bloc `<script>` (cassée depuis l'ajout du script anti-flash).

## Vérification fonctionnelle plus large (ad hoc)

Pattern des tests ponctuels : script Node avec DOM factice (`document.querySelector` renvoyant des éléments cachés dans une Map, stubs `localStorage`/`window`) + `vm.runInThisContext` sur le `<script>` principal extrait — puis appel direct des fonctions de l'app (`startFree()`, `passQ()`, `submit()`, `startReview()`, …) et assertions sur `state`/`stats`. C'est cette approche qui a détecté le bug « question posée qui revenait trop tôt ».
